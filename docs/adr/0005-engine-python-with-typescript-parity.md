# ADR-0005 · Engine in Python, with a TypeScript slice for offline use

- **Status:** Accepted
- **Date:** 2026-09-17

## Context

The engine decides what a student does next. The product spec requires that the
same state and engine version always produce the same result, and that practice
keeps working offline — where the next item is chosen in reaction to each answer.

Splitting the engine by what must run offline:

| Engine part | Offline? |
| --- | --- |
| Priority ranking, prerequisite substitution, planner rules | No — the plan is generated server-side and prefetched |
| Item selection ladder | **Yes** |
| Mastery update per answer | **Yes** |
| Help ladder (check again → hint → solution → micro-lesson) | **Yes** |
| Review scheduling, score ranges, mock repair | No |

Running Python in the browser (Pyodide) would add several megabytes to first load,
which the device and data budgets rule out.

## Decision

- **`packages/engine` (Python)** is the single source of truth: pure functions, no
  I/O, seeded randomness, versioned by `ENGINE_VERSION`.
- **`packages/engine-ts` (TypeScript)** implements only the offline slice: mastery
  update, item ladder, help rules.
- **`packages/fixtures`** holds vectors generated by the Python engine:
  `state + attempt → expected rating, expected next level, expected help action`.
  Both test suites run them; TypeScript asserts within 1e-9 to allow for
  floating-point differences in `exp`.
- The parity harness is built in **sprint S2, before the offline work in S3**.
- Any change to a shared rule regenerates the vectors in the same pull request. CI
  fails if the two implementations disagree, or if vectors are stale.

## Consequences

- Two implementations of the most safety-critical rules exist. This is accepted, and
  contained by the vectors: divergence fails CI instead of quietly serving students
  the wrong questions.
- Rules that only run server-side stay in Python alone. Keep the TypeScript slice as
  small as possible; everything else belongs behind the API.
- `ENGINE_VERSION` is stamped on every derived record, so any state can be rebuilt
  by replay under a known version.

## Alternatives considered

- **Pyodide in the browser.** Megabytes of download on a metered connection.
- **Rust or Go engine compiled to WebAssembly, bound to both.** Removes duplication
  and adds a third language for arithmetic that is a handful of formulas.
- **Server-generated decision trees** (precomputed "if correct go here" bundles).
  Keeps the client dumb, but the bundle generator becomes complex and long offline
  stretches degrade badly.
- **No offline adaptivity.** Cheapest, and breaks the product promise for students
  with intermittent data.
