# ADR-0006 · SQL-first schema with raw SQL migrations

- **Status:** Accepted
- **Date:** 2026-09-17

## Context

`database/migrations/001_curriculum.sql` already defines the curriculum schema in
hand-written SQL: composite foreign keys that keep a curriculum item inside one
syllabus version, check constraints on statuses and hashes, partial unique indexes,
and views. The syllabus loader derives deterministic UUIDs and verifies the source
PDF's SHA-256 before writing.

These constraints are the product's integrity guarantees. An ORM's model layer
cannot express several of them, and generated migrations would quietly weaken them.

The student event tables to come (`attempts` and the rest) are append-only and
queried analytically, which is SQL-shaped work rather than object-graph work.

## Decision

- The database schema is defined by **numbered `.sql` files** in
  `database/migrations`, applied in order, each wrapped in a transaction and safe to
  re-run.
- A small Python runner applies them and records applied versions in a
  `schema_migrations` table. No Alembic, no ORM-generated migrations.
- Application code reads and writes through **SQLAlchemy Core** with explicit SQL.
  No ORM models, no lazy loading.
- Constraints live in the database. Application checks are a convenience for error
  messages, never the only guard.
- Derived tables (ratings, plans, opportunities, score ranges, metrics) carry
  `engine_version` and can be rebuilt by replaying events.

## Consequences

- Schema review happens in SQL, where the constraints are visible.
- More typing than an ORM for simple reads; explicit joins everywhere.
- Migrations can use anything PostgreSQL offers: partitioning, generated columns,
  exclusion constraints, partial indexes.
- The existing Ruby loader keeps working until the content tooling replaces it in
  S1; it uses `psql` and needs no gems.

## Alternatives considered

- **SQLAlchemy ORM + Alembic.** Autogenerated migrations drift from hand-written
  constraints, and the schema's composite keys fight the model layer.
- **Django ORM.** Would require rewriting the schema in models, losing constraints
  that models cannot express.
- **Prisma or another external schema language.** A second source of truth for a
  schema that already exists in SQL.
